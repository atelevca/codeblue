# Оркестрация обработки аудио: задания, профили записей, уверенность ASR

Дата: 2026-09-26
Статус: дизайн согласован, готов к планированию реализации

## 1. Зачем

Сегодня конвейер рассчитан ровно на один файл: `IProcessedAudioFiles.FindFirst()` берёт первый
по алфавиту файл из общей папки, результаты пишутся в фиксированные пути `transcripts/<имя>.*`,
а HTTP-запрос висит до конца обработки. Дальше появляется UI с загрузкой файла, и такая форма
перестаёт работать: две загрузки подряд перетирают друг друга, браузер отваливается по таймауту
на длинной записи, прогресса не видно вообще.

Одновременно накопились три содержательные доработки, которые логично внести тем же заходом,
пока структура всё равно меняется: разные типы записей со своими словарями, передача в LLM
информации о том, где распознавание было неуверенным, и список известных фонетических ошибок.

Цель: пользователь загружает файл, выбирает тип записи, видит ход обработки в процентах,
получает диалог с расставленными спикерами и исправленными терминами и может указать,
какой врач скрывается за каждым «Speaker N».

## 2. Область работ

**Входит.** Задания с изоляцией артефактов; оркестрация на WorkflowCore с персистентностью
в SQLite; сервис прогресса по шагам плюс детальный прогресс внутри распознавания; профили
записей (свой initial_prompt, свой системный промпт, свой набор глоссариев); пометка
неуверенно распознанных слов и передача её в LLM-коррекцию; файл известных фонетических
ошибок; справочник врачей и ручная привязка спикеров; новый job-API взамен четырёх
текущих эндпоинтов.

**Не входит.** Аутентификация и разграничение доступа. Работа на macOS (Metal вместо Vulkan) —
отложено сознательно, разработка идёт под Windows; требование к коду одно: не углублять
привязку к Vulkan, чтобы будущий переезд остался заменой пакета и одной ветки в конфиге.
Автоматическое опознание спикеров по голосу. Сам UI — здесь только API под него.
Наполнение глоссариев для финансовых и административных записей.

**Тесты не пишутся.** Правило проекта из `CLAUDE.md`: тестовых проектов, файлов и кода в
репозитории быть не должно. Проверка — запуском приложения и вызовом эндпоинтов, см. раздел 13.

## 3. Изоляция заданий

Самое крупное изменение в существующем коде. Каждое задание получает свой каталог:

```
assets/input/<jobId>/<исходное имя>
assets/processed/<jobId>/<имя>.wav          полноценный WAV, частота и каналы как в оригинале
assets/processed/<jobId>/<имя>.16k.wav      вход для моделей: 16 кГц, моно
transcripts/<jobId>/<имя>.json
transcripts/<jobId>/<имя>.diarization.json
transcripts/<jobId>/<имя>.speakers.json
transcripts/<jobId>/<имя>.medical_corrections.md
```

`IProcessedAudioFiles.FindFirst()` удаляется. Сервисы перестают искать файл сами и начинают
принимать явный путь. Внутренняя логика сервисов при этом не меняется — меняется только то,
откуда они узнают, с чем работать.

Файл `<имя>.16k.wav` — новый производный артефакт. Его пишет тот же ffmpeg с `-ar 16000 -ac 1`,
и дальше VAD, Whisper и диаризация читают именно его. `AudioSampleReader` сам пропускает
преобразование, когда формат уже совпал с целевым, поэтому чтение становится почти бесплатным
и повторное декодирование на каждом шаге перестаёт быть проблемой. Основной WAV остаётся
побитово верным исходнику — правило из `CLAUDE.md` о сохранении исходной частоты и каналов
не нарушается, потому что относится именно к нему.

## 4. Хранилище

Два отдельных файла SQLite:

```
data/workflow.db      WorkflowCore: свои таблицы, своя схема, свой EF-провайдер
data/healthtech.db    наши три таблицы: Dapper поверх Microsoft.Data.Sqlite
```

Разделение не косметическое. Хост WorkflowCore постоянно опрашивает своё хранилище, в том числе
на простое; запросы статуса из UI идут часто. В одном файле эти два потока рано или поздно
встретились бы на блокировке SQLite (`SQLite Error 5: 'database is locked'`), причём падал бы
обычно короткий запрос из UI. В разных файлах встречаться им негде.

На обоих подключениях всё равно включается `journal_mode=WAL` и `busy_timeout=5000` — дёшево
и снимает остаток риска.

`WorkflowCore.Persistence.Sqlite` построен на EF Core, поэтому EF останется в графе пакетов.
Наш код его не использует: схема наших таблиц создаётся скриптом, доступ — через Dapper.

### Схема

Один файл `schema.sql`, прогоняется при старте, идемпотентен:

```sql
CREATE TABLE IF NOT EXISTS Jobs (
    Id           TEXT PRIMARY KEY,
    FileName     TEXT NOT NULL,
    ProfileKey   TEXT NOT NULL,
    Status       TEXT NOT NULL,          -- Pending | Running | Completed | Failed
    CurrentStep  TEXT NULL,
    Percent      INTEGER NOT NULL DEFAULT 0,
    WorkflowId   TEXT NULL,
    Error        TEXT NULL,
    CreatedAt    TEXT NOT NULL,
    CompletedAt  TEXT NULL
);

CREATE TABLE IF NOT EXISTS Persons (
    Id        TEXT PRIMARY KEY,
    FullName  TEXT NOT NULL,
    Specialty TEXT NULL
);

CREATE TABLE IF NOT EXISTS SpeakerBindings (
    JobId        TEXT NOT NULL,
    SpeakerLabel TEXT NOT NULL,           -- "Speaker 1"
    PersonId     TEXT NOT NULL,
    PRIMARY KEY (JobId, SpeakerLabel)
);
```

Справочник врачей наполняется тем же скриптом через `INSERT OR IGNORE` — эндпоинта на добавление
нет сознательно, записи заводятся руками. Файл `healthtech.db` при необходимости открывается
любым редактором SQLite.

`Jobs` — единственный источник правды для UI. Шаги workflow пишут в него, UI опрашивает только
его и про внутренности WorkflowCore ничего не знает.

## 5. Workflow

### Данные между шагами

WorkflowCore сериализует данные workflow в хранилище на каждом переходе, поэтому передавать
между шагами массивы сэмплов нельзя — только пути и идентификаторы:

```csharp
public class TranscriptionJobData
{
    public Guid   JobId { get; set; }
    public string ProfileKey { get; set; } = "";
    public string SourcePath { get; set; } = "";
    public string NormalizedPath { get; set; } = "";
    public string Wav16kPath { get; set; } = "";
    public List<SpeechChunkDto> Chunks { get; set; } = [];
    public string TranscriptPath { get; set; } = "";
    public string DiarizationPath { get; set; } = "";
    public string SpeakersPath { get; set; } = "";
}
```

`Chunks` — несколько десятков пар секунд, сериализуется дёшево.

### Шаги и веса

| # | Шаг | Вес | Накопленный % |
|---|---|---:|---:|
| 1 | `NormalizeAudioStep` — ffprobe + ffmpeg → `<имя>.wav` | 5 | 5 |
| 2 | `PrepareModelInputStep` — ffmpeg → `<имя>.16k.wav` | 5 | 10 |
| 3 | `DetectSpeechChunksStep` — Silero VAD → список чанков | 5 | 15 |
| 4 | `TranscribeStep` — Whisper по чанкам → `<имя>.json` | 40 | 55 |
| 5 | `DiarizeStep` — sherpa → `<имя>.diarization.json` | 20 | 75 |
| 6 | `AlignSpeakersStep` — выравнивание и слияние реплик | 3 | 78 |
| 7 | `CorrectTermsStep` — LLM → `<имя>.medical_corrections.md` | 20 | 98 |
| 8 | `SaveResultStep` — `<имя>.speakers.json`, финализация записи | 2 | 100 |

Каждый шаг по завершении обновляет `Jobs.CurrentStep` и `Jobs.Percent`.

### Детальный прогресс внутри распознавания

Шаг 4 занимает большую часть времени, и без дополнительной работы полоса замерла бы на 15%
до самого конца распознавания. Поэтому `ISpeechRecognitionService.TranscribeAsync` получает
параметр `IProgress<double>?` с долей 0..1 внутри шага, а сам цикл по чанкам в
`ProcessedAudioTranscriptionService` докладывает после каждого чанка.

Шаг пересчитывает долю в свою полосу:

```
Percent = 15 + 40 * fraction
```

Наружу, помимо процента, отдаётся человекочитаемое `CurrentStep`, например
`"Распознавание: чанк 7 из 42"`.

Аналогичный коллбэк имеет смысл и в шаге 7 (по батчам LLM, полоса 78–98%) — там тоже
десятки минут на длинной записи.

### Ошибки

Падение шага переводит задание в `Failed`, в `Error` кладётся сообщение из
`AudioProcessingException` или `LlmModelNotFoundException`. Автоматический ретрай не включаем:
шаги дорогие, и повторять распознавание часовой записи из-за сбоя модели смысла нет — человек
перезапустит задание сам.

## 6. Профили записей

Тип записи выбирается при загрузке файла и хранится в `Jobs.ProfileKey`. Профиль определяет
четыре вещи сразу: направляющую фразу для Whisper, системный промпт коррекции, набор глоссариев
и файл фонетических ошибок.

```
Profiles:
  consilium:
    DisplayName:      "Консилиум (общий)"
    WhisperPrompt:    "Discuție între doi colegi din spital, în română, cu cuvinte rusești..."
    SystemPromptFile: "Prompts/medical_correction.system.txt"
    Glossaries:       [ "medical_glossary.txt", "moldova_speech_glossary.txt" ]
    PhoneticFile:     "phonetic_confusions.txt"
  onco:
    DisplayName:      "Онкология"
    WhisperPrompt:    <направляющая фраза под онкологию, пишется на шаге 7 реализации>
    SystemPromptFile: "Prompts/medical_correction.system.txt"
    Glossaries:       [ "medical_glossary.txt", "onco_glossary.txt", "moldova_speech_glossary.txt" ]
    PhoneticFile:     "phonetic_confusions.txt"
  icu:
    DisplayName:      "Интенсивная терапия"
    WhisperPrompt:    <направляющая фраза под ОИТ, пишется на шаге 7 реализации>
    SystemPromptFile: "Prompts/medical_correction.system.txt"
    Glossaries:       [ "medical_glossary.txt", "icu_glossary.txt", "moldova_speech_glossary.txt" ]
    PhoneticFile:     "phonetic_confusions.txt"
```

Оба специализированных профиля прирастают к общему `medical_glossary.txt`, а не заменяют его:
термины из кардиологии и общей практики в записях ОИТ и онкологии встречаются ровно так же.

Отсюда следует то, что надо проверить при реализации. `MaxGlossaryCharacters` (по умолчанию 2000)
применяется в `MedicalTermCorrector.BuildUserMessage` **к каждому файлу отдельно**, поэтому
третий глоссарий не вытесняет общий словарь, а увеличивает запрос ещё на 2000 символов.
Вместе с `MaxBatchCharacters` (4000) и системным промптом это даёт порядка 12 тысяч символов
на запрос. Текст кириллический и румынский с диакритикой, то есть токенов на символ уходит
заметно больше, чем на английском, а `Llm:ContextSize` = 8192 и `MaxTokens` = 2048
зарезервированы под ответ. Запас есть, но он сокращается. При добавлении профиля с третьим
глоссарием нужно один раз посчитать реальную длину запроса в токенах и при необходимости
опустить `MaxGlossaryCharacters` до 1200–1500 либо поднять `ContextSize`.

Важное ограничение по `WhisperPrompt`: whisper.cpp обрезает initial_prompt примерно на
224 токенах (половина текстового контекста). Это не настройка, а свойство декодера. Значит
туда кладётся направляющая фраза — язык, жанр речи, десяток-другой самых частых терминов
домена, — а не глоссарий. Основная терминология работает на этапе LLM-коррекции.

### `IProfileCatalog`

Новый синглтон: ключ → готовый `RecordProfile` с уже разобранными глоссариями. Разбор
850 строк `medical_glossary.txt` делается один раз при старте, а не на каждый запрос.

```csharp
public record RecordProfile(
    string Key,
    string DisplayName,
    string WhisperPrompt,
    string SystemPrompt,
    IReadOnlyList<Glossary> Glossaries,
    Glossary? Phonetics);
```

Неизвестный ключ профиля при создании задания → 400.

### Что меняется в существующих сервисах

`WhisperSpeechRecognitionService.TranscribeAsync` начинает принимать промпт параметром —
сейчас он берётся из `WhisperOptions.Prompt` в конструкторе. Значение из конфига остаётся
как запасное для профилей без своей фразы.

`MedicalTermCorrector` перестаёт грузить три файла-константы из `AppContext.BaseDirectory`
(`MedicalTermCorrector.cs:19-21`) и получает профиль в параметрах `CorrectAsync`. Заголовки
глоссариев переезжают в описание профиля.

Имя `MedicalTermCorrector` пока сохраняется: оба профиля медицинские, название не врёт.
Переименование имеет смысл, когда реально появится финансовый или административный тип.

## 7. Уверенность распознавания

### Что доступно

Whisper.net 1.9.1 не отдаёт n-best гипотезы — ни в `SegmentData`, ни в билдере ничего похожего
нет, и это ограничение самого whisper.cpp, а не обёртки. Доступна вероятность каждого токена:
`WithProbabilities()` включает её, `SegmentData.Tokens[]` содержит текст и вероятность.

### Сборка слов

Токены — подсловные куски («аторв», «а»). Слова собираются так: токен, начинающийся с пробела,
открывает новое слово, остальные приклеиваются к текущему. Вероятность слова — **минимум** по
его токенам: для пометки подозрительных мест нужен консервативный агрегат.

Смещения считаются не по токенам, а поиском собранных слов в итоговом тексте сегмента
последовательно от курсора. Текущий код тримит `segment.Text`, и склейка токенов может не
совпасть с текстом посимвольно; поиск от курсора устойчив к этому расхождению.

Слова с вероятностью ниже `Whisper:LowConfidenceThreshold` (по умолчанию 0.5) попадают в
результат:

```csharp
public record LowConfidenceWord(int At, string Word, double P);
```

Тип живёт в `SemanticKernel.MedicalCorrection` рядом с `Segment` — так его видят оба проекта
без дублирования и слоя преобразования.

### Как смещения переживают склейки

Это самое кропотливое место всей работы; смещение пересчитывается на каждой из трёх склеек.

1. **Чанк → файл.** Текст сегмента не меняется, смещения остаются. Сдвигаются только
   временные метки, как сейчас.
2. **Сегменты → реплика** (`ProcessedAudioSpeakerTranscriptService.Align`). При слиянии
   `last.Text + " " + text` смещения присоединяемого сегмента сдвигаются на
   `last.Text.Length + 1`.
3. **Реплика → куски** (`MedicalTermCorrector.SplitIntoPieces`). Абсолютное начало куска
   уже известно из накопленной длины предыдущих частей. Слова, попавшие в
   `[начало куска, начало + длина)`, переносятся в кусок со смещением `At - начало`.

### Что уходит в LLM и в файлы

В запросе к модели каждый кусок получает список подозрительных слов:

```json
{
  "id": 7,
  "text": "pacientul are аторва статин 20 mg",
  "lowConfidence": [
    { "at": 14, "word": "аторва",  "p": 0.31 },
    { "at": 21, "word": "статин", "p": 0.44 }
  ]
}
```

То же поле сохраняется в `<имя>.json` и `<имя>.speakers.json`, чтобы
`POST /audio/correctTranscript` работал по уже готовому файлу так же, как полный прогон,
и не приходилось перезапускать Whisper ради переподбора глоссария.

В системный промпт добавляется абзац: перечисленные слова распознаны неуверенно и с наибольшей
вероятностью являются ошибками, начинать следует с них, но явную ошибку вне списка исправить
тоже можно. Мягкая подсказка, а не запрет — обоснование в разделе 14.

## 8. Файл фонетических ошибок

Формат совпадает с глоссарием, поэтому `Glossary.Load` и `Glossary.Select` переиспользуются
без единой правки: `Select` ищет по всем колонкам кроме последней, то есть и по услышанному
варианту, и по правильному.

```
# Известные ошибки распознавания
# услышано | правильно | комментарий
аторва статин | аторвастатин | разрыв слова
mio cardic    | miocardic    | разрыв слова
эка ге        | ЭКГ          | аббревиатура
```

Новый заголовок в запросе к модели:

> Known ASR mishearings (left = what the recognizer produces, right = the correct form):

Файл задаётся профилем и пополняется вручную по отчётам `<имя>.medical_corrections.md`.

## 9. Привязка спикеров

Диаризация по-прежнему выдаёт `Speaker 1`, `Speaker 2`, … в порядке появления. После обработки
UI показывает список меток задания и справочник врачей, человек сопоставляет их вручную;
результат ложится в `SpeakerBindings`.

`GET /jobs/{id}/transcript` отдаёт диалог с подставленными именами; метки без привязки остаются
как есть. Сами файлы транскриптов не переписываются — привязка живёт только в базе, поэтому её
можно менять сколько угодно раз без перезапуска обработки.

Автоматическое опознание по голосу не делается, но путь открыт: в C#-обёртке sherpa-onnx есть
`SpeakerEmbeddingExtractor` и `SpeakerEmbeddingManager`, а нужная модель
`wespeaker_en_voxceleb_resnet34_LM.onnx` и так в списке обязательных.

## 10. API

```
GET    /profiles                 список профилей для выпадашки при загрузке
POST   /jobs                     multipart: file + profileKey → { jobId }
GET    /jobs                     список заданий
GET    /jobs/{id}                { status, currentStep, percent, error }
GET    /jobs/{id}/result         транскрипт со спикерами
GET    /persons                  справочник врачей
PUT    /jobs/{id}/speakers       [{ label: "Speaker 1", personId }]
GET    /jobs/{id}/transcript     диалог с подставленными именами
POST   /audio/correctTranscript?fileName=&profile=
```

Контроллеры остаются тонкими: принять запрос, вызвать сервис, вернуть результат. Вся проверка,
ветвления и обработка ошибок — в сервисах, отображение доменных исключений в HTTP — в
`IExceptionHandler`. Правило проекта из `CLAUDE.md`.

`POST /jobs` создаёт запись в `Jobs`, кладёт файл в `assets/input/<jobId>/` и запускает
workflow, после чего сразу возвращает `jobId`. Ждать обработки запрос не должен.

Четыре текущих эндпоинта — `validateAndProcess`, `transcribeProcessed`, `diarizeProcessed`,
`transcribeWithSpeakers` — удаляются: с каталогами по заданиям «первый файл в общей папке»
перестаёт иметь смысл, а держать два параллельных пути ради демо незачем.
`correctTranscript` остаётся и получает параметр профиля — он позволяет крутить глоссарии
и промпты, не переплачивая каждый раз за распознавание.

## 12. Порядок реализации

1. **Каркас заданий и оркестрации.** Каталоги по заданиям, две базы, схема, `Jobs`, workflow
   из восьми шагов с весами, `POST /jobs` и `GET /jobs/{id}`. Существующие сервисы переводятся
   на явные пути. К концу шага загруженный файл проходит весь конвейер, а прогресс виден.
2. **Коллбэк прогресса** внутри распознавания и коррекции.
3. **Профили.** `IProfileCatalog`, секция конфига, проброс промпта в Whisper и профиля
   в корректор. Содержательно — пока один профиль `consilium` на текущем контенте.
4. **Уверенность ASR.** `WithProbabilities()`, сборка слов, три пересчёта смещений, поле
   в файлах и в запросе к модели, абзац в промпте.
5. **Фонетический список.** Файл, заголовок, подключение к профилю.
6. **Справочник и привязка спикеров.**
7. **Профили `onco` и `icu`**: по глоссарию и направляющей фразе на каждый, плюс замер
   реальной длины запроса в токенах (см. раздел 6).

Пункты 1 и 2 — фундамент, остальное на него опирается. Пункты 4 и 5 независимы друг от друга
и от 6, их порядок можно менять.

## 13. Проверка

Тесты не пишутся (правило проекта). Проверка ручная, запуском приложения:

- загрузка файла через `POST /jobs` с каждым из трёх профилей; задание доходит до `Completed`;
- `GET /jobs/{id}` во время обработки показывает растущий процент и меняющийся шаг, в том
  числе внутри распознавания;
- две загрузки подряд не мешают друг другу: артефакты лежат в разных каталогах;
- `<имя>.json` содержит `lowConfidence` на тех словах, которые на слух действительно
  сомнительные;
- `<имя>.medical_corrections.md` показывает, что термины из глоссария профиля подхватились;
- `POST /audio/correctTranscript` по готовому файлу даёт тот же результат, что полный прогон;
- падение шага (например, при отсутствующей модели) переводит задание в `Failed` с внятным
  сообщением, а не роняет приложение;
- `PUT /jobs/{id}/speakers` меняет имена в `GET /jobs/{id}/transcript` без перезапуска обработки.

## 14. Решение, принятое по умолчанию

Одно, и оно не подтверждалось явно — если это не так, менять дёшево.

**Строгость правок по уверенности.** `lowConfidence` подаётся модели как подсказка, а не как
запрет: правку вне списка `CorrectionValidator` по-прежнему пропускает. Причина в том, что
низкая вероятность токена ловит не все ошибки — Whisper регулярно выдаёт беглое частое слово
вместо редкого термина с высокой уверенностью, и жёсткий запрет оставил бы такие случаи
неисправленными навсегда. Ужесточение (проверка пересечения изменённого участка со списком)
добавляется в `CorrectionValidator` позже, если на реальных записях окажется много ложных
правок.
